# Sync Engine v2: suspected bugs to verify

Found by reading code during the prior-art review (2026-11-28). None has been reproduced yet. Each one gets a failing test first; then it is either fixed or struck off as not a bug. Line numbers are approximate and from the commit at the time.

| # | Suspected bug | Where | Spec | How to reproduce |
|---|---|---|---|---|
| 1 | **Idempotency key changes when queued commands are merged.** The key is built from the sorted IDs of the merged commands. A command sent alone (key `a`) that timed out, then merged with a later command, is resent under key `a,b` with a different body, so the server runs it again. | `frontend/src/stores/commandQueue.ts` ~314, ~549 | `SYNC-G-102` | Send a command, drop its response, enqueue an update to the same object, flush; assert the server applied the first command once. |
| 2 | **A sent create followed by a delete cancels out locally.** If the create reached the server but its response was lost, coalescing removes both commands; the object survives on the server and reappears on the next sync. | `frontend/src/api/coalesceCommands.ts` ~92 | `SYNC-G-102`, `SYNC-G-303` | Create, drop the response, delete while offline, reconnect; assert the object is gone on the server. |
| 3 | **A sent create merged with an update loses the update.** The merged command is a create; the server's `insert_conflict` treats it as a replay of the existing row and drops the new fields. | `frontend/src/api/coalesceCommands.ts`; `backend/app/services/events/create.rb` ~108 | `SYNC-G-102`, `SYNC-P-3` | Create, drop the response, rename while offline, reconnect; assert the server has the new name. |
| 4 | **409 for an in-flight duplicate is treated as a rejection.** The server answers 409 while the same idempotency key is still being processed; the client doesn't treat 409 as retryable, so it undoes a change that was in fact applied. | `backend/app/routes/api.rb:21`; `frontend/src/stores/commandQueue.ts` ~30 | `SYNC-G-102`, `SYNC-G-601` | Hold the first request open on the server, let the client time out (15s) and retry; assert the client keeps the change. |
| 5 | **429 is not retryable.** Invites are rate-limited to 10 per minute; flushing more than 10 queued invites rejects the rest permanently. `Retry-After` is ignored. | `backend/lib/rate_limiter.rb` ~110; `frontend/src/stores/commandQueue.ts` ~30 | `SYNC-G-104`, `SYNC-G-603` | Queue 11 invites offline, reconnect; assert all 11 are eventually sent. |
| 6 | **Idempotency keys effectively live 24–48 hours.** TTL is 24h but rows are only removed by a daily prune. After expiry, a queued update is applied again and can overwrite later edits by others. Conflicts with `SYNC-G-803` (no maximum offline duration). | `backend/app/services/maintenance/prune_expired.rb` ~28 | `SYNC-G-102`, `SYNC-G-803` | Apply an update, let another user edit the field, expire the key, retry the first update; assert the other user's edit survives. |
| 7 | **No jitter on command retries; little on reconnect.** Command retries back off 5s to 60s without jitter; WebSocket reconnect adds only 0–1s of jitter. After a deploy every client reconnects, flushes and catches up within a second or two. | `frontend/src/stores/commandQueue.ts` ~177; `frontend/src/stores/websocket.ts` ~501 | `SYNC-G-1108` | Unit test on the backoff schedule; load test after a server restart. |
| 8 | **The client parses the server's sync timestamp and compares it with its own clock.** | `reconcileCursor` in `frontend/src/stores/websocket.ts` | `SYNC-P-7` | Fake the client clock an hour off; assert sync behaves the same. |
| 9 | **Catch-up can skip rows committed around a sync.** The cursor is the server's `Time.now`, and rows are selected by `updated_at`, which is set at transaction start, not commit. | `backend/app/services/sync/workspace_sync.rb` ~28 | `SYNC-G-302` | RSpec with two connections: open transaction A and write, commit B, sync, commit A, sync; assert A arrives. |
| 10 | **Pending updates are cleared by comparing a server timestamp with a client timestamp.** A wrong phone clock keeps changes pending too long or clears them too early. | `importObjects` in `frontend/src/stores/objectPool.ts` ~504–517 | `SYNC-P-7`, `SYNC-G-403` | **Reproduced** (clock ahead): known-gap test in `frontend/src/stores/objectPool.spec.ts`. Clock behind still to do. |
